# 波形存储系统：问题清单与改进路线

> 建立日期：2026-07-24  
> 基线：首次目录整理和 Git 初始化版本  
> 状态说明：`OPEN` 未处理，`PARTIAL` 已做保护性修改但未完整解决，`DONE` 已完成并验证。

## 1. 优先级定义

| 级别 | 含义 |
|---|---|
| P0 | 阻断核心链路、可能产生错误数据，或存在必须立即处理的凭据风险 |
| P1 | 高概率导致现场不稳定、卡死、难排障或数据不一致 |
| P2 | 明显增加维护成本，妨碍测试、发布或扩展 |
| P3 | 代码质量、界面体验和长期工程化改进 |

## 2. P0：核心阻断问题

### WF-001：统一 GUI 与采集端的 ZMQ 协议

- 状态：`PARTIAL`
- 现状：
  - GUI 使用 `DEALER`；
  - 采集端使用 `PULL`；
  - GUI 等待响应，采集端不响应；
  - GUI 发送 `频率,时长,[设备列表]`，采集端执行 `int(message)`。
  - 2026-07-25 线上只读调查确认，生产 `saveApp` 监听 `0.0.0.0:5000`，
    且日志能解析客户端、频率、时长和设备；但 socket 类型、响应内容和幂等语义仍未知。
- 已处理：
  - 新增本地版本化 JSON 候选协议，包含 UUID 请求 ID、命令、频率、秒级时长和设备列表；
  - 请求/响应执行严格字段校验，并定义 accepted/running/终止状态转换；
  - 新增协议编解码、非法输入和状态转换测试；
  - 候选协议尚未接入 GUI、采集原型或生产 `saveApp`，现有 legacy 消息保持不变。
- 影响：仓库内 GUI 与采集原型无法直接通信；生产服务表现出部分兼容性，但当前协议无法在
  本地复现、自动测试或安全演进，仍是完整采集链路的首要阻断项。
- 建议：
  1. 统一为 `DEALER/ROUTER` 或 `REQ/REP`；
  2. 使用版本化 JSON 消息；
  3. 增加 `request_id`、命令、设备、频率、时长和协议版本；
  4. 定义接收、拒绝、执行中、成功、失败状态；
  5. 明确超时、重复请求和重试语义。
- 验收标准：
  - GUI 能发送一条合法请求并收到结构化响应；
  - 非法字段返回明确错误码；
  - 相同 `request_id` 重试不会启动两次采集；
  - 有协议单元测试和 fake server 集成测试。

- 现状：

  - 生产服务端源码、启动方式、响应协议和采集后续阶段仍未进入当前仓库或得到确认。
- 影响：无法确认谁负责排队、触发、拉取、转换、进度和最终回复。
- 建议：建立 `acquisition/server.py`，把通信层与采集任务层分开。
- 验收标准：
  - 服务可持续监听多个请求；
  - 单次任务全阶段可观测；
  - 异常时资源被释放；
  - 支持优雅停止；
  - 服务重启后能识别未完成任务。

### WF-003：移除和轮换历史明文凭据

- 状态：`PARTIAL`
- 已处理：活动主线改为从环境变量读取密码；原始 ZIP和历史源码默认不进入 Git。

  3. 使用系统密钥环、Vault 或部署平台 secret；
  4. 增加 secret scanning；
  5. 确认首次提交中不存在凭据。
- 验收标准：
  - 旧密码失效；
  - `git grep` 和 secret scanner 无发现；
  - 生产部署不需要在源码或普通配置文件中保存密码。

### WF-005：定义并验证 HDF5 schema

- 状态：`PARTIAL`
- 已完成：
  - 新增可识别版本的 HDF5 v2 reader/writer，保存 `uint64` bunchID、X/Y、缺失掩码、
    设备映射、跳过原因、质量报告、对齐参数和调用方元数据；
  - 新增单 BPM、v2 和 legacy 合并格式 round-trip 与错误 schema 测试；
  - legacy GUI 导出已修复 `int32` 中间转换及跳过设备后的属性错位；
  - v2 采用 `.part` 临时文件加原子替换，legacy 格式无法表达缺失单元时明确拒绝写入。
- 现状：
  - 单 BPM 文件假定 1024 点；
  - 合并文件按设备交错保存 X/Y；
  - dtype、单位、缩放和属性命名没有正式文档；
  - 2026-07-25 已对一份线上真实文件完成只读 header 检查：
    `BunchIDData` 为 `uint64 (1,1024)`，`Data` 为 `int64 (2,1024)`，
    根属性为 `Device`、`Data_0=bpm_x`、`Data_1=bpm_y`。
  - 同一文件的 1,024 个 bunchID 全部非零、唯一且严格递增；X/Y 中存在正常零值，
    但单位和缩放仍未确认。
- 影响：可能产生结构合法但语义错误的数据文件。
- 建议：
  1. 定义 schema 版本；
  2. 明确 dataset 形状、dtype、单位、缩放和缺失值；
  3. 每行数据与设备元数据建立明确索引；
  4. 保存来源文件、采集时间、软件版本和处理参数；
  5. 为旧数据提供读取兼容层。
- 验收标准：
  - schema 文档和测试 fixture 齐全；
  - 写入后重新读取并校验所有字段；
  - 被跳过的设备不会出现在有效数据映射中；
  - 不同版本文件可识别。

## 3. P1：稳定性与数据正确性

### WF-006：重写 bunchID 对齐算法的边界处理

- 状态：`PARTIAL`
- 线上证据：
  - 一份真实样例使用数值约为 `3.8e13` 的 `uint64` bunchID；
  - 该样例无零值、无重复且严格递增；
  - X/Y 的真实数据中存在零值，不能与 bunchID 零值规则混用。
  - 2025-11-12 12:07:21 同批 36 台设备的 shape、dtype 和长度一致，但严格交集为 0；
  - 33 台设备的步长为 500,000，另有 3 台使用 61/75/76 一类步长，说明至少存在两种
    不兼容的 bunchID 编码或时基，尚不能直接认定这 3 台为坏设备。
  - 500,000 步长组内部严格交集仍为 0；覆盖统计显示约 30 台主簇和 3 台完全错窗设备。
- 已完成：
  - 新增不依赖 Qt、SSH、HDF5 或 matplotlib 的对齐纯函数；
  - strict/coverage 均保留 `uint64`，输出 `valid_mask`、跳过原因和质量报告；
  - 选择结果按设备 ID 稳定排序，不依赖输入顺序；
  - 已覆盖空输入、无交集、零值、重复、乱序、长度错误和冲突簇等离线测试。
- 风险：
  - 空输入会访问 `sets_list[0]`；
  - 无交集会访问 `indices_matrix[0]`；
  - 第一个设备含 0 时基准集合和原索引可能错位；
  - 重复 bunchID 使用 `.index()` 只取第一次；
  - `.index()` 逐项搜索复杂度高；
  - “低于 50% 就跳过设备”的规则没有业务确认。
  - 覆盖率模式无法自行解决不同 bunchID 空间，未经确认的缩放或取模会制造错误对齐。
- 建议：把算法改为纯函数，输入带设备标识的结构化记录，输出结果、跳过原因和统计信息。
- 验收标准：
  - 覆盖空、单设备、无交集、含 0、重复 ID、乱序和异常长度；
  - 输出设备顺序稳定；
  - 每个跳过设备都有原因；
  - 规则参数化且有说明。

## 7. 开工前必须回答的问题

1. 正式采集服务器是哪一台，是否存在未放入当前目录的服务端代码？
2. 采集时长的业务单位是秒还是分钟？
3. 哪些频率是正式支持值，等待时间如何计算？
4. 每个 BPM 的文件完成标志是什么？
5. 原始文件是否始终 1024 点？
6. X/Y 除以 1000 后的单位是什么？
7. bunchID 是否唯一、递增，是否允许 0？
8. 50% 交集阈值是否是经过确认的业务规则？
9. 全局锁是保护设备、保护服务器，还是仅防止 GUI 重复点击？
10. 数据保留周期、磁盘容量和权限边界是什么？

这些答案应进入正式的协议、配置和数据 schema 文档，避免继续依赖源码中的隐含规则。
