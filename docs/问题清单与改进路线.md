# 波形存储系统：问题清单与改进路线

> 建立日期：2026-07-24  
> 基线：首次目录整理和 Git 初始化版本  
> 状态说明：`OPEN` 未处理，`PARTIAL` 已做保护性修改但未完整解决，`DONE` 已完成并验证。

## 1. 优先级定义

| 级别 | 含义 |
|---|---|
| P0 | 阻断核心链路、可能产生错误数据，或存在必须立即处理的凭据风险 |
| P1 | 高概率导致现场不稳定、卡死、难排障或数据不一致 |
| P2 | 明显增加维护成本，妨碍测试、发布或扩展 |
| P3 | 代码质量、界面体验和长期工程化改进 |

## 2. P0：核心阻断问题

### WF-001：统一 GUI 与采集端的 ZMQ 协议

- 状态：`OPEN`
- 现状：
  - GUI 使用 `DEALER`；
  - 采集端使用 `PULL`；
  - GUI 等待响应，采集端不响应；
  - GUI 发送 `频率,时长,[设备列表]`，采集端执行 `int(message)`。
- 影响：两端无法直接通信，是完整采集链路的首要阻断项。
- 建议：
  1. 统一为 `DEALER/ROUTER` 或 `REQ/REP`；
  2. 使用版本化 JSON 消息；
  3. 增加 `request_id`、命令、设备、频率、时长和协议版本；
  4. 定义接收、拒绝、执行中、成功、失败状态；
  5. 明确超时、重复请求和重试语义。
- 验收标准：
  - GUI 能发送一条合法请求并收到结构化响应；
  - 非法字段返回明确错误码；
  - 相同 `request_id` 重试不会启动两次采集；
  - 有协议单元测试和 fake server 集成测试。

### WF-002：补齐真正的采集服务端

- 状态：`OPEN`
- 现状：项目只有只收一次消息的 ZMQ 试验脚本和一个 `PULL` 采集原型，没有与 GUI 协议兼容的完整服务。
- 影响：无法确认谁负责排队、触发、拉取、转换、进度和最终回复。
- 建议：建立 `acquisition/server.py`，把通信层与采集任务层分开。
- 验收标准：
  - 服务可持续监听多个请求；
  - 单次任务全阶段可观测；
  - 异常时资源被释放；
  - 支持优雅停止；
  - 服务重启后能识别未完成任务。

### WF-003：移除和轮换历史明文凭据

- 状态：`PARTIAL`
- 已处理：活动主线改为从环境变量读取密码；原始 ZIP和历史源码默认不进入 Git。
- 未处理：
  - 原 ZIP 和本地历史文件仍包含旧凭据；
  - 旧凭据是否已失效未知；
  - 当前仍允许密码认证。
- 影响：一旦归档外泄，可能直接暴露内部主机权限。
- 建议：
  1. 立即轮换所有曾写入源码的凭据；
  2. 优先使用受限 SSH key；
  3. 使用系统密钥环、Vault 或部署平台 secret；
  4. 增加 secret scanning；
  5. 确认首次提交中不存在凭据。
- 验收标准：
  - 旧密码失效；
  - `git grep` 和 secret scanner 无发现；
  - 生产部署不需要在源码或普通配置文件中保存密码。

### WF-004：确认唯一正式主线和现场地址

- 状态：`OPEN`
- 现状：`main.py`、`main_zyf.py` 使用不同服务端和锁路径，无法仅靠代码判断正式版本。
- 影响：重构时可能连接错误服务器或破坏现场互斥策略。
- 建议：由现场负责人确认 GUI 主版本、ZMQ 地址、存储地址、锁目录和正式数据根目录。
- 验收标准：形成一份经过确认的部署配置，不再通过源码分支区分现场环境。

### WF-005：定义并验证 HDF5 schema

- 状态：`OPEN`
- 现状：
  - 单 BPM 文件假定 1024 点；
  - 合并文件按设备交错保存 X/Y；
  - dtype、单位、缩放和属性命名没有正式文档；
  - 跳过 BPM 时元数据可能与数据行错位。
- 影响：可能产生结构合法但语义错误的数据文件。
- 建议：
  1. 定义 schema 版本；
  2. 明确 dataset 形状、dtype、单位、缩放和缺失值；
  3. 每行数据与设备元数据建立明确索引；
  4. 保存来源文件、采集时间、软件版本和处理参数；
  5. 为旧数据提供读取兼容层。
- 验收标准：
  - schema 文档和测试 fixture 齐全；
  - 写入后重新读取并校验所有字段；
  - 被跳过的设备不会出现在有效数据映射中；
  - 不同版本文件可识别。

## 3. P1：稳定性与数据正确性

### WF-006：重写 bunchID 对齐算法的边界处理

- 状态：`OPEN`
- 风险：
  - 空输入会访问 `sets_list[0]`；
  - 无交集会访问 `indices_matrix[0]`；
  - 第一个设备含 0 时基准集合和原索引可能错位；
  - 重复 bunchID 使用 `.index()` 只取第一次；
  - `.index()` 逐项搜索复杂度高；
  - “低于 50% 就跳过设备”的规则没有业务确认。
- 建议：把算法改为纯函数，输入带设备标识的结构化记录，输出结果、跳过原因和统计信息。
- 验收标准：
  - 覆盖空、单设备、无交集、含 0、重复 ID、乱序和异常长度；
  - 输出设备顺序稳定；
  - 每个跳过设备都有原因；
  - 规则参数化且有说明。

### WF-007：修复合并 HDF5 元数据错位

- 状态：`OPEN`
- 现状：代码计算了过滤后的 `devicename_new`，但写属性时仍遍历原始设备名。
- 影响：当某 BPM 被跳过，属性可能描述错误的数据行。
- 验收标准：对照输入设备、被跳过设备和最终数据行，逐项验证 X/Y 映射一致。

### WF-008：把网络和数据处理移出 GUI 主线程

- 状态：`OPEN`
- 现状：SSH `find`、SFTP 下载、HDF5 读取、对齐、保存和 `sleep()` 都在按钮回调中。
- 影响：网络慢或数据量大时窗口冻结，用户可能重复点击或强制关闭。
- 建议：使用 `QThread`、`QRunnable/QThreadPool` 或独立服务；通过 Qt signal 更新进度。
- 验收标准：
  - 长任务期间窗口仍可拖动和取消；
  - 按钮状态与任务状态一致；
  - 关闭窗口可以安全中止或转后台；
  - 不从工作线程直接修改控件。

### WF-009：改进 SSH 资源管理和主机校验

- 状态：`OPEN`
- 现状：
  - 使用 `AutoAddPolicy()`；
  - 多处没有可靠关闭 SFTP/SSH；
  - 错误分支可能泄漏连接；
  - 远程命令由字符串拼接形成。
- 影响：主机冒充风险、连接泄漏和难以定位的超时。
- 建议：校验 known_hosts，使用上下文管理器和统一 SSH gateway。
- 验收标准：
  - 未知 host key 默认拒绝；
  - 所有成功和失败路径都关闭连接；
  - 连接/命令/传输超时可配置；
  - 日志保留主机、阶段和异常类型。

### WF-010：正确选择远程采集文件

- 状态：`OPEN`
- 现状：采集端使用 `sftp.listdir()[0]`，没有过滤、排序或完成标志。
- 影响：可能下载旧文件、临时文件或仍在写入的文件。
- 建议：定义文件命名协议和完成语义，例如临时后缀后原子改名，或 sidecar manifest。
- 验收标准：
  - 目录为空时返回明确状态；
  - 只选请求对应设备和采集批次的文件；
  - 不读取写入中的文件；
  - 重复轮询不会重复入库。

### WF-011：修复采集时长计算

- 状态：`OPEN`
- 现状：把 `YYYYMMDDHHMMSS` 当整数相减，跨分钟、小时和日期均不可靠。
- 建议：使用 `time.monotonic()` 控制持续时间，用 timezone-aware `datetime` 记录事件时间。
- 验收标准：跨分钟、午夜和系统时间校正时仍按预期结束。

### WF-012：为 TXT 输入增加严格校验

- 状态：`OPEN`
- 现状：只处理恰好三列的行，固定创建 1024 点 dataset，却不验证有效行数。
- 风险：静默丢行、shape 不匹配、溢出和单位错误。
- 验收标准：
  - 行数、列数、数值范围和 dtype 都校验；
  - 错误文件进入隔离区并记录原因；
  - 明确 X/Y 除以 1000 的物理单位；
  - 写入采用临时文件加原子改名。

### WF-013：统一任务锁与状态机

- 状态：`OPEN`
- 现状：GUI 文件锁、JSON 状态、采集端循环和多个历史锁原型并存。
- 影响：GUI 按钮锁定不等于采集任务真实状态；客户端崩溃时可能出现假锁或重复采集。
- 建议：锁由服务端持有，GUI 展示服务端任务状态；本地按钮只防抖。
- 验收标准：
  - 任意客户端都能查询统一任务状态；
  - 服务崩溃/重启后状态可恢复；
  - 超时、取消和失败都有明确迁移；
  - 不依赖共享 JSON 的非原子读写。

### WF-014：处理设备排序未知项

- 状态：`OPEN`
- 现状：使用 `pv_list_sorted.index(x)`，远程文件出现未知设备时直接抛异常。
- 建议：建立 `device_name -> order` 映射，对未知项给出策略。
- 验收标准：未知、重复和缺失设备不会让整批处理崩溃。

### WF-015：建立可诊断日志

- 状态：`OPEN`
- 现状：大量 `print()` 和裸 `except`，错误信息常为 `something wrong`。
- 建议：统一使用 `logging` 或结构化日志。
- 验收标准：
  - 每个请求有 request ID；
  - 日志包含阶段、设备、远端、耗时和异常堆栈；
  - 密码不进入日志；
  - 可配置级别、轮转和保存位置。

## 7. 开工前必须回答的问题

1. 正式采集服务器是哪一台，是否存在未放入当前目录的服务端代码？
2. 采集时长的业务单位是秒还是分钟？
3. 哪些频率是正式支持值，等待时间如何计算？
4. 每个 BPM 的文件完成标志是什么？
5. 原始文件是否始终 1024 点？
6. X/Y 除以 1000 后的单位是什么？
7. bunchID 是否唯一、递增，是否允许 0？
8. 50% 交集阈值是否是经过确认的业务规则？
9. 全局锁是保护设备、保护服务器，还是仅防止 GUI 重复点击？
10. 数据保留周期、磁盘容量和权限边界是什么？

这些答案应进入正式的协议、配置和数据 schema 文档，避免继续依赖源码中的隐含规则。
