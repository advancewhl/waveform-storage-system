### 1.3 线上消息和 BPM 连接行为

`nohup.out` 中至少记录了两次请求：

```text
2026-03-15 19:19:40：2 Hz，600 s，12 台 BPM
2026-06-03 11:23:26：2 Hz，600 s，1 台 BPM
```

日志包含客户端 ID、频率、时长、开始时间和设备列表对应的 PV，因此可以确认生产
`saveApp` 能解析当前 GUI 风格的复合请求；不能仅凭服务端日志确认 GUI 是否收到了结构化
或非结构化回复。

本地 GUI 的直接代码证据为：

- `zmq_client_dealer.py` 使用 `DEALER`，并把客户端本机 IP 设置为 ZMQ identity；
- `main.py` 发送 `频率,界面时长数值,[设备列表]`；
- 客户端发送后等待服务端回复。

线上日志中的 `client_id`、`Frequence`、`interval` 和设备 PV 与这些字段逐项对应。日志把
一次 GUI 时长显示为 `600 s`，很可能由服务端把界面分钟数换算为秒，但在取得原始请求帧
或线上源码前仍不能确认具体换算位置。

这两次日志均以 `no BPM connect` 结束，没有证据表明任务完成了触发、TXT 下载或 HDF5
写入。日志还反复出现：

- EPICS CA 服务端无响应；
- TCP 连接被对端重置；
- caproto 在断开状态收到 `EchoResponse`；
- `RESULT_CAPTURE` PV 仍处于 searching 状态。

受影响地址覆盖 `192.0.2.15` 至 `192.0.2.24` 中的多台主机，日志所示 EPICS CA
端口为 6310。这里只能确认当时的连接失败，不能推断这些设备当前仍然不可用。

日志打印了 `timestr - start_time`，与本地采集原型中把 `YYYYMMDDHHMMSS` 当整数相减的
风险相符；尚未取得线上源码或反编译证据，不能确认实现完全相同。

`nohup.out` 的最后修改时间为 2026-06-03 11:23:39。进程仍在运行只证明操作系统中的


前 32 个 bunchID 的相邻步长均为 500,000；最小值到最大值的跨度也等于
`1023 × 500,000`，说明这份样例的整列很可能为等步长序列。下一轮多文件统计会直接验证
完整差分集合，当前不把“所有线上文件均等步长”当作事实。

- bunchID 为 0：可能表示无效 ID，需要按业务规则处理；
- X/Y 为 0：在真实数据中正常出现，不能自动当作缺失值。

这些数值是 HDF5 中实际存储的整数；在单位和缩放规则得到现场确认前，不把它们标记为
微米、纳米或其他物理单位。

### 1.5 同批多 BPM 对齐基线

对 2025-11-12 12:07:21 批次执行了只读统计，共得到 36 个文件和 36 个唯一设备。所有
设备均满足：

```text
BunchIDData: uint64, shape=(1024,)
Data:        int64,  shape=(2, 1024)
bunchID 为 0 的数量：0
bunchID 唯一值数量：1024
bunchID 严格递增：True
```

但 bunchID 步长存在三个集合：

```text
33 台设备：                         [500000]
AC_LA_L1_BI_COLDBPM01/02：          [75, 76]
AC_LA_COL0_BI_SBPM07：              [61, 75, 76]
```

把 36 台设备直接做精确严格交集，结果为：

```text
strict_intersection_count = 0
```

这说明该批次“全设备严格共同 bunchID”不可用，但不能直接把三台不同步长设备标记为坏
设备。当前证据更符合“设备间存在不同 bunchID 编码、量纲或时基”的描述。必须先确认这些
设备的 bunchID 语义，再决定：

- 将不同编码体系分别对齐；
- 使用经过验证的转换关系归一化；
- 或在明确质量规则下排除不兼容设备。

禁止仅为了得到非空交集而猜测缩放、取模、四舍五入或强制转换。覆盖率模式也只能解决
设备缺失某些 ID，不能自动解决不同 ID 空间。

进一步按步长分组后发现，步长相同也不等于采集窗口兼容：



这表明现场批次至少包含：

1. 约 30 台设备的主覆盖簇；
2. 3 台同为 500,000 步长、但与主簇窗口完全错开的设备；

主簇的设备和原因；簇选择不得依赖文件或设备输入顺序。
